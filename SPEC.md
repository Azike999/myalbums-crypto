# My Albums — как устроено шифрование

[English](SPEC.en.md) · состояние на 27.11.2026 · `crypto.js` SHA-256 `54ad03d1…ec7c7e1`

Всё ниже описано по коду, а не по памяти. Форматы проверяются примерами из `test_vectors.json` двумя
независимыми программами (`tests/`). Если код и этот текст разойдутся, прав код. Сообщите нам об этом (`SECURITY.md`).

## 1. Коротко

- У каждого человека есть **основной ключ** — 32 случайных байта. Он создаётся на телефоне и на наш сервер
  открытым не попадает.
- Фото, видео и все сведения о них (подпись, дата, место, люди, имя файла) шифруются на телефоне
  **AES-256-GCM** до отправки. Сервер и хранилище получают только шифр.
- Всё делает стандартный WebCrypto браузера (`crypto.subtle`). Своей криптографии нет, кроме SHA-256,
  написанного на JavaScript для меток дубликатов больших файлов (п. 3.4). Результат тот же, что у WebCrypto,
  и это проверяется.
- Чего это не гарантирует, честно описано в п. 10 «Ограничения».

## 2. Ключи

| Ключ | Откуда | Чем защищён, где лежит |
|---|---|---|
| Основной | 32 байта `crypto.getRandomValues` | См. п. 5. На сервер — никогда в открытом виде |
| Ключ дубликатов | `SHA-256(основной ‖ "dedup")` | Вычисляется, не хранится |
| Ключ файла | 32 случайных байта на каждый файл | Внутри сведений о фото (`fk`), которые зашифрованы ключом альбома |
| Ключ секретного альбома | 32 случайных байта | Заперт ключом из пароля (PBKDF2), лежит в зашифрованном каталоге. Основным ключом **не** заперт нарочно: разблокированного телефона мало, нужен пароль |
| Ключ общего альбома | 32 случайных байта, не зависит от основного | У владельца — в каталоге. Участникам — ECIES на их открытую половину (п. 3.6). Гостям по ссылке — PBKDF2 от кода |
| Пара ECDH P-256 человека | `generateKey` | Открытая половина — на сервере открыто. Закрытая — на сервере, заперта основным ключом |

**Код восстановления** — сам основной ключ в base32 (алфавит RFC 4648 без `=`): 52 знака группами по 4.
При вводе прощаются строчные буквы, пробелы, цифры 0/1/8 вместо O/I/B и похожие кириллические буквы
(`normB32` в `crypto.js`).

## 3. Алгоритмы и форматы

### 3.1 Небольшие данные: превью, миниатюры, сведения о фото, каталог
AES-256-GCM, случайный IV 12 байт. Результат: `IV(12) ‖ шифротекст ‖ метка GCM(16)`.
GCM проверяет целостность: чужой ключ или испорченный байт — отказ, а не «мусор». По этому отказу приложение
узнаёт неверный код или пароль.

### 3.2 Большие файлы и видео: кусочный формат `PBC1`
Файл режется на куски по 1 МиБ, каждый кусок шифруется отдельно. Так видео можно перематывать без полной
загрузки, а телефону не нужно держать весь файл в памяти.

```
заголовок 32 байта: "PBC1" | размер куска u32 (1048576) | длина открытого файла u64 | 8 случайных байт | 8 нулей
кусок i:            AES-256-GCM, IV = 8 случайных байт заголовка ‖ u32(i), AAD = заголовок ‖ u32(i)
файл:               заголовок ‖ кусок 0 ‖ кусок 1 ‖ …   (у каждого куска своя метка 16 байт)
```
AAD с номером куска и заголовком не дают переставить куски, подставить кусок из другого файла или незаметно
обрезать файл. Это тоже проверяется в `tests/check_vectors.mjs`.

### 3.3 Ключ файла
С 26.09.2026 у каждого файла свой случайный ключ. Им шифруются оригинал, превью 2048 px и миниатюра 400 px.
Сам ключ лежит в сведениях о фото, а они зашифрованы ключом альбома. Перенос фото в другой альбом
перешифровывает только сведения, а не файл. У файлов, загруженных раньше, ключа файла нет: они зашифрованы
ключом альбома.

### 3.4 Метка дубликата
`HMAC-SHA256(ключ дубликатов, байты файла)`. Сервер сравнивает метки и не принимает тот же файл дважды. Для
секретных и общих альбомов метка дополнительно пропускается через HMAC ключом дубликатов альбома (`albumTag`):
так сервер не свяжет фото с его копией в другом альбоме. Для больших файлов HMAC считается по кускам
(`dedupStream`, SHA-256 на JavaScript). Результат равен обычному HMAC, это проверяется.

### 3.5 Пароли: секретный альбом, общий альбом под паролем, код гостевой ссылки
`PBKDF2-HMAC-SHA256`, 300 000 итераций, соль 16 случайных байт, пароль приводится к NFKC. 32 байта
результата — ключ AES-GCM, которым заперт 32-байтный ключ альбома (п. 3.1). Код гостевой ссылки — 80 случайных
бит (16 знаков base32), запирается так же.

### 3.6 Передача ключа другому человеку или устройству: ECIES `E1`
Разовая пара ECDH P-256 отправителя и открытая половина получателя → общий секрет 256 бит → `HKDF-SHA256`
(соль 16 случайных байт, info `"myalbums-shared-v1"`) → AES-256-GCM.
Запись: `E1.<открытый ключ отправителя, 65 байт>.<соль>.<IV>.<шифротекст>`, каждая часть в base64.
Используется для ключа общего альбома участнику, основного ключа новому устройству (п. 6) и половины A
доверенному человеку (п. 8).

### 3.7 Проверочные цифры от подмены открытого ключа
- **Код безопасности общего альбома:** 10 цифр из SHA-256 открытой половины участника (≈ 33 бита). Одинаков на
  обоих экранах, сверяется голосом.
- **Проверка при подключении устройства:** 4 цифры из SHA-256 открытой половины нового устройства (п. 6 и п. 10).
- **Код доверенного человека** (`heirCode`): 16 цифр из первых 8 байт SHA-256 открытой половины доверенного
  (≈ 53 бита). Доверенный вычисляет свой код из **своей закрытой** половины (`pubFromPrivEnc`), а не берёт открытую
  с сервера: иначе подменивший сервер показал бы обоим одинаковые цифры чужого ключа.

## 4. Что шифруется

На телефоне до отправки шифруются:
- **Файлы:** оригинал, превью 2048 px, миниатюра 400 px. У видео кадр-обложка — это превью.
- **Сведения о каждом фото** (одна зашифрованная запись): имя файла, тип, подпись, дата съёмки, координаты,
  ширина и высота, длительность видео, исходный размер, альбом, отметки людей, описания лиц для подсказок
  «кто на фото», ключ файла и метка содержимого.
- **Каталог:** названия альбомов, обложки, имена людей, ключи секретных и общих альбомов, векторы поиска
  по содержимому.
- **Общий альбом:** название, обложка, описание и прочие сведения альбома — ключом альбома. Реакции участников
  (какой значок и к какому фото) — тоже ключом альбома.

Подсказки лиц, поиск по содержимому, определение места по координатам (встроенный справочник мест),
HEIC, видео-обложки — всё считается на телефоне. Карты и чужие сервисы геокодирования не вызываются.

## 5. Где хранится основной ключ

| Где запущено | Где ключ |
|---|---|
| Мини-приложение в Телеграме | Облачное хранилище Telegram (CloudStorage — привязано к аккаунту Telegram и нашему боту; у Bot API нет способа его прочитать) **и** `localStorage` устройства |
| Приложение для iPhone | Связка ключей iOS (`AfterFirstUnlockThisDeviceOnly`, не уходит в iCloud) и `localStorage` |
| Приложение для Android | Зашифрован ключом из AndroidKeyStore, хранится в настройках приложения; резервное копирование Android выключено |
| Браузер | `localStorage` |

Ключ хранится в открытом виде (base64) в CloudStorage и `localStorage`: оттуда его берёт код страницы.
**Telegram технически может прочитать ключ из CloudStorage.** Это осознанный выбор: без него ключ терялся бы
вместе с телефоном. Подробнее в п. 10.

На наш сервер ключ уходит только запертым:
- при подключении устройства (п. 6, ECIES на ключ нового устройства);
- в конверте доверенного человека (п. 8);
- закрытая половина пары ECDH и копии ключей общих альбомов — заперты основным ключом.

## 6. Как ключ переезжает на новое устройство

1. **Тот же аккаунт Telegram** — ключ сам находится в CloudStorage.
2. **Код восстановления** — 52 знака, набрать или вставить.
3. **Подключение устройства без Телеграма** (приложение iPhone или Android, браузер):
   - новое устройство создаёт разовую пару ECDH P-256 и отдаёт серверу открытую половину;
   - человек подтверждает подключение в мини-приложении в Телеграме, где ключ уже есть. Мини-приложение запирает
     основной ключ на эту открытую половину (ECIES, п. 3.6) и отдаёт серверу только запертое;
   - новое устройство забирает запертый ключ (одноразово, заявка живёт 10 минут) и открывает его своей закрытой
     половиной;
   - на обоих экранах видны 4 одинаковые цифры: если сервер подменил открытую половину, цифры, скорее всего,
     разойдутся. Слабое место этой проверки — в п. 10.

## 7. Если ключ потерян

Восстановить ключ на сервере нельзя: копии у нас нет. Если нет ни кода восстановления, ни аккаунта Telegram
с CloudStorage, ни устройства, где ключ ещё есть, фото потеряны. Приложение может создать новый ключ, но старые
файлы им не открыть. Частичные пути назад:
- **доверенный человек** после срока молчания (только смотреть, секретные альбомы недоступны);
- **общие альбомы** — их ключ есть у других участников.

Забытый пароль секретного альбома не восстанавливается вообще.

## 8. Доверенный человек («два из двух»)

Если хозяин не заходит выбранное число месяцев, доступ «только смотреть» получает выбранный им человек.
Телефон хозяина (`heirSeal`):
- создаёт ключ конверта E и случайную половину A, B = E xor A;
- конверт C = AES-GCM(E, основной ключ);
- A запирается на открытую половину доверенного (ECIES).

Сервер хранит C, B и запертую A. Серверу не хватает A, доверенному до срока не хватает B, сервер отдаёт её
только после срока. Доверенный (`heirOpen`): A — своей закрытой половиной, E = A xor B, основной ключ = открыть C.
Перед печатью хозяин и доверенный сверяют 16 цифр (п. 3.7) — по телефону или при встрече. Телефон хозяина
запирает половину A только после «Код совпал». До 27.11.2026 печать шла автоматически, без сверки (п. 10).

## 9. Что сервер видит открыто

Шифрование скрывает содержимое, но не всё вокруг него. Сервер знает:
- **аккаунт:** номер (ID), имя, имя пользователя и язык в Telegram; часовой пояс; платформу (iPhone, Android,
  браузер); тариф и платежи; откуда человек пришёл впервые;
- **активность:** в какие дни открывалось приложение (первое и последнее время), названия пройденных шагов
  (например, «пригласил в общий альбом»);
- **файлы:** сколько их; точные размеры оригинала, превью и миниатюры (по длине шифра); фото это или видео;
  время загрузки; метки дубликатов. Сервер видит повторную загрузку того же файла, в том числе при проверке
  перед загрузкой выбранных файлов;
- **общие альбомы:** кто владелец, кто участники и с какими ролями, кто пришёл по ссылке, какое фото в каком
  общем альбоме, кто его загрузил, кто и когда поставил реакцию (но не какую);
- **даты для напоминаний:** день «Портрета года» (месяц и число — часто это день рождения); дата открытия
  капсулы времени; субботы ближайших недель, на которые есть «воспоминания» из прошлых лет;
- **доверенный человек:** кто чей доверенный, срок, даты;
- **подключённые устройства:** название («Chrome · Windows»), платформа, даты;
- **вопросы ИИ-помощнику Кадрику:** текст вопроса и ответа. Они уходят ИИ-сервису (Anthropic) и хранятся у нас
  до 90 дней без привязки к аккаунту. Фото и подписи Кадрику не отправляются, но если в вопросе написать имя или
  место, оно попадёт туда открытым.

### Когда сервер видит сам файл открытым
Только по действию человека, только его собственный файл:
- **«В чат», «Отправить» и «Скачать» в Телеграме на Android** (в том числе коллаж и ролик). Браузер Telegram
  на Android не умеет сохранять файлы, поэтому телефон расшифровывает файл и отдаёт его серверу. Сервер передаёт
  его в Telegram или отдаёт по разовой ссылке. Для «Скачать» файл лежит на диске сервера до 15 минут, имя файла
  видно в ссылке и в журнале запросов;
- **фото, присланные боту в чат.** Их получает Telegram, и сервер видит их как обычные сообщения бота. Имя, тип,
  дата и подпись хранятся открыто до 7 дней, пока приложение не заберёт фото. Само фото проходит через сервер
  к телефону, а телефон шифрует его и загружает как обычно.

## 10. Ограничения — чего код не гарантирует

1. **Код страницы приходит с нашего сервера.** Это веб-приложение. Приложения для iPhone и Android тоже
   открывают страницу с сервера, а не держат её внутри себя. Взломанный или недобросовестный сервер может однажды
   отдать подменённый `crypto.js` или `app.js`, и тот отправит ключ. Этого не решил полностью ни один веб-сервис
   со сквозным шифрованием.
   - **Чем закрываем сейчас.** Шифрование открыто здесь и отдаётся байт в байт, его можно сверить `verify.py`.
     Отдельная проверка раз в час со стороны (не с нашего сервера) сравнивает всё, что получает телефон, с
     выпущенной версией и сообщает о расхождении. Сам сервер тоже раз в час сверяет свои файлы. Политика CSP не
     даёт странице выполнять чужие скрипты (кроме скрипта Telegram).
   - **Чего это не закрывает.** Сверка одного `crypto.js` не доказывает, что `app.js` не отправит ключ: `app.js`
     закрыт и отдаётся сжатым, а два небольших файла (видео по частям на iPhone и подбор лучших кадров) запутаны.
     Подменённый код можно отдать выборочно одному человеку — общая проверка его не увидит. Скрипт Telegram
     (`telegram-web-app.js`) загружается с серверов Telegram.
   - **Чем можно закрыть.**
     - публиковать SHA-256 каждой выпущенной версии здесь и в журнале изменений;
     - подключать `crypto.js` с `integrity="sha256-…"` (SRI);
     - встроить `crypto.js` и проверку хешей в само приложение для iPhone и Android, чтобы оно не брало код
       шифрования с сервера;
     - независимый аудит.
2. **Telegram может прочитать основной ключ** из CloudStorage, как и любой, кто завладел аккаунтом Telegram.
   Код гостевой ссылки и сама ссылка по умолчанию отправляются одним сообщением через Telegram. Ключ гостя
   сохраняется в его CloudStorage.
3. **Проверка подмены ключей короткая или необязательная.** Это защита от недобросовестного сервера, который
   подменяет открытые ключи, не меняя код:
   - **подключение устройства:** 4 цифры. Подобрать пару ключей с теми же 4 цифрами — около 10 000 попыток,
     то есть секунды;
   - **доверенный человек:** с 27.11.2026 конверт запечатывается только после сверки 16 цифр (п. 8). Конверты,
     запечатанные раньше, сделаны без сверки: сервер, который хранит B, мог тогда подставить свою половину. Чтобы
     перестраховаться, доверенного можно назначить заново;
   - **общий альбом:** код безопасности 10 цифр показывается, но сверять его не обязательно.
4. **Метаданные открыты** — см. п. 9: размеры, время, общий граф участников общих альбомов, даты напоминаний.
5. **Код восстановления — это сам ключ** (256 бит, без пароля). Кто его увидел, получил всё.
6. **Разблокированный телефон** с открытым Telegram открывает архив. Секретные альбомы требуют пароль.
7. **Бывший участник общего альбома** сохраняет ключи файлов, которые уже видел.
8. **Резервные копии базы** хранятся 31 день. В них то, что перечислено в п. 9, и запертые копии ключей
   (не открытые).
